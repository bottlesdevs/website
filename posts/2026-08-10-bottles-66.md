Only a few days have passed since Bottles 65 and I am already here writing about Bottles 66, because once the first corrections were out I returned to an idea that has been following Bottles for years and finally found the right way to make it work.

That idea is UMU, but before getting there I need to talk about Bottles Next and about the name we will use for the Bottles you already know.

## Bottles Next is close

Work on Bottles Next is moving forward and the situation today is very different from the first announcement. We have a working core, a new dependency distribution system that avoids storing and downloading the same files several times and a graphical toolkit built on Rust and Iced which is close to containing every widget needed by the new client; the foundations are there, the pieces are talking to each other and Bottles Next is genuinely around the corner, although that does not mean tomorrow or the day after tomorrow.

It also cannot simply arrive and replace an application with nine years of history, millions of installations and a way of working people have built their setups around. Bottles will turn ten next year and the current application still has work to do, users to support and features that make sense today, therefore leaving it without UMU while waiting for Next would have served nobody.

## Bottles Legacy, not a deprecated Bottles

Now that Next is close enough for both applications to be discussed at the same time, calling one "Bottles" and the other "Bottles Next" has become misleading, because it makes the second sound like the update that will eventually erase the first. From now on I will refer to the current Bottles, the one we have all been using until today, as **Bottles Legacy**.

Legacy does not mean abandoned or deprecated, Bottles 65 and this release should make the opposite fairly clear; it simply gives a precise name to the existing application while we prepare another one with a different architecture. Bottles Next will itself offer two ways of working: Classic mode will preserve the bottle management people know from Legacy, with a different interface and the new features made possible by the new core, while Next mode will use the central Bottles concept where every program, its dependencies and its configuration live as separate layers over a managed bottle.

The [original Bottles Next announcement](/blog/2023-10-05-bottles-next-a-new-chapter) explains those two modes and the architecture behind them in more detail. The important part here is that Classic and Next are two experiences inside Bottles Next, while Bottles Legacy is the application available today and it will not disappear when the new one becomes usable.

This is also why bringing UMU to Legacy had become almost necessary. I first wrote about its possible integration in 2024, when there were still too many questions and every answer seemed to require turning Bottles into a different application; Bottles Legacy is built around bottles where you can install several programs and control the whole Windows environment, while UMU uses Proton to prepare and launch one game at a time, applying the fixes collected for that specific title. Both approaches make sense, but mixing them without a clear separation would have made both worse.

Bottles 66 finally gives UMU its own place without hiding it in a submenu and without asking it to pretend to be a normal bottle.

## UMU arrives in the Library

UMU is developed by [Open Wine Components](https://github.com/Open-Wine-Components), the group created to improve the Wine gaming ecosystem through shared projects and of which Bottles is also a member. It brings the Steam Linux Runtime and the environment expected by Proton outside Steam, therefore a launcher can start a game through Proton in the same kind of container used by Steam without requiring Steam itself or adding the title to its Library.

The Library can now install a Windows game through UMU. You search for the title, Bottles recognizes it through the UMU database and guides you through the installer, then the game appears beside everything else you already launch from Bottles with its cover, controls and a small badge showing where it came from.

If the game is known, UMU also knows which Proton fixes belong to it; this is the part that matters much more than having another way to open an `.exe`, because titles that need a particular configuration can receive it automatically instead of making every user rediscover the same solution. If a game is not in the database you can still add it as a custom title, so the catalog helps when it has something useful to say without becoming a wall when it does not.

![UMU games inside the Bottles Library](/uploads/bottles-66/umu-library.png)

Each game keeps its own Proton version and launch settings, including arguments, environment variables and working directory, while the UMU page in Preferences lets you choose the defaults for new installations. Bottles also detects existing UMU prefixes and shows them in the main view, therefore games created elsewhere do not need to disappear just because you opened another launcher.

Dependencies can come from the Bottles catalog or from winetricks, depending on what the game needs and what you prefer to use. Protonfixes remains automatic and connected to the game itself, while anything you install manually remains visible in its settings; the distinction may sound obvious, but it avoids the usual situation where something was installed months ago and nobody remembers which tool changed the prefix.

The same UMU support is available from the command line for anyone who manages games through scripts or a terminal, but the graphical experience remains the main one: search, install, wait for the process to finish and find the game in the Library.

## ProtoSoda

There was still one problem. UMU is made for Proton and Soda is a Wine runner, so using UMU meant leaving behind the runner I maintain specifically for Bottles and choosing another Proton build.

ProtoSoda is my answer to that.

It combines the Proton environment expected by UMU with the Wine core from Soda 11.0-5, keeping the work already done for native Wayland, 32-bit prefixes, multimedia, mod loaders and the other corrections introduced with Bottles 65. In practice UMU sees the Proton structure it needs, while the Windows program runs through Soda; this is also why ProtoSoda is a separate runner rather than another Soda version with a different name.

Bottles installs ProtoSoda through the usual component manager and uses it as the default for new UMU games, but nothing is locked, each title can use a different compatible Proton build when needed. ProtoSoda also has its own section and logo in the runner manager, and the official Bottles runners now show their identity beside the selected version instead of looking like another anonymous archive in the list.

## Soda starts learning

Soda 11.0-5 also begins a different kind of runner work. Adaptive Launch is the first in a series of updates dedicated to making Soda smarter, so it can understand the programs it runs instead of treating every launch as completely new.

When you enable it for a bottle, Soda keeps a small profile of the files that program actually uses while it starts. On later launches Bottles can ask the system to prepare those files earlier, which can help programs with a large runtime, many libraries or a busy prefix reach their first window with less waiting. It does not change the game configuration, install anything or promise an FPS increase; it only gives the next launch a better idea of where it is going.

This is deliberately a first step. The profile is local to the bottle and is built from what you launch, so there is no shared database guessing what a game needs and no invisible tuning applied behind your back. The option requires `soda-11.0-5` or newer, and Bottles keeps it unavailable on older Soda builds because they do not support the profile safely yet.

## cpak joins the official packages

Flatpak has been the only official Bottles package for years and it remains the recommended, most tested way to install the application. Bottles 66 adds a second one through [cpak](https://cpak.it/store/Utilities/github.com/bottlesdevs/bottles), a container format I have been developing since 2023 around direct Linux desktop integration and packages that keep their origin and permissions easy to inspect, and which I also [presented at GUADEC](https://www.youtube.com/live/fDXPD4R85Ds?t=3603&si=E_L6D9jvl6KfS7dn) when the idea was still much younger than the package available today.

The cpak package is **Experimental**. I want people to try it, report where the experience still differs from Flatpak and help decide what the format needs before I present it as a normal installation choice. It is already built from the same source tree and release tag as Bottles, receives UMU as a direct package dependency and is recognized by Bottles as an official package, so this is a real distribution path rather than a detached community recipe.

Bottles can start there without a Wine runner already installed, keeps separate cpak instances independent and uses the packaged UMU integration without asking the user to assemble the environment. The download page now offers both official packages while keeping the experimental label visible on cpak, because having a second option should never hide which one has years of production use behind it.

## What changed after Bottles 65

The first four maintenance updates are all included in Bottles 66. Opening bottle settings no longer fails on systems without GameMode, ordinary programs are no longer presented to Proton as fake Steam games and Proton 11 can use the newer Steam Runtime 4 it expects.

Creating a bottle also works when its template does not install any component or contains both Wine registry profiles, the dependency page opens without freezing the interface and cancelled back gestures no longer discard the page you were using. Deleting a bottle now closes its confirmation dialog correctly, while Proton 11 receives the missing VKD3D utility needed by its updated graphics stack.

Several installers that use cabinet archives can now find files through wildcard paths, program icons and Library covers no longer overwrite each other, Flatpak add-ons use the correct installation command and Bottles can connect through SOCKS proxies. The cover chooser opens in Pictures, as one would reasonably expect, and NVK is detected correctly inside the Flatpak for users running the open NVIDIA driver.

I also reworked component updates after the reports received with Bottles 65. Update suggestions now have one clear application setting, the bulk update window tells you what is current, what can be updated and what failed, and runners and graphics components follow the same process instead of spreading the state across different bottle pages.

The issue form check has been corrected, the build workflows have been updated and the icons needed by the new UMU pages, official runners and version badges are now shipped with Bottles, so their appearance no longer depends on which icon theme happens to be installed on the system.

Bottles 66 started as the place where I would collect the fixes released after 65, then UMU found the shape it had been missing, ProtoSoda became the bridge between that new experience and the runner I wanted to keep, and cpak became the second official way to install it.

Apparently "maintenance mode" means something slightly different around here.
