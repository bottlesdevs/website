![Soda 11, now even fizzier](/uploads/bottles-65/soda-now-even-fizzier.png)

I am not entirely sure how I got to this release, Bottles was supposed to stay in maintenance while we worked on Bottles Next and the plan was to keep shipping small updates, a few fixes and the usual component updates, then a few weeks ago I reopened the tracker and started checking every report against the code to understand which ones were still valid and which ones described a Bottles that no longer exists.

Things got slightly out of hand from there (in the best possible way), because one issue led to an old pull request, that pull request uncovered another part that needed work and in the meantime new ideas kept arriving for Soda, Eagle and the features many of you have been asking for; eventually I had done enough work to make the name 64.2 look ridiculous, so here I am with Bottles 65.

![Bottles 65 with Soda 11](/uploads/bottles-65/bottle-details.png)

Over these weeks I closed 180 issues and went through 34 pull requests across the Bottles repositories, some became fixes while others were duplicates or belonged to Wine, components, dependencies or the Windows program itself, and several valid pull requests opened by contributors were recovered, corrected where needed and merged. I also tightened the issue template and added an automatic check for reports that arrive without the information needed to start looking at the code.

Ok.. with some cleaning out of the way, I can talk about the fun part.

## Eagle now has a memory

With Bottles 61 I introduced Eagle Analysis, a tool that tries to understand an executable before launching it by opening the file and looking at what it contains, which technologies it uses, whether it hides an installer or other files and whether anything inside it could need attention under Wine; Eagle has always been about avoiding the idea that every `.exe` is a black box and giving the user more information before the usual dance of attempts, overrides and dependencies begins.

![Eagle analysing an executable](/uploads/bottles-65/eagle-analysis.png)

Local analysis only knows what it can find inside the file though, it does not know whether other people have already tried that game, which configuration worked more often or whether a certain version started causing trouble, so Bottles 65 introduces Eagle Intelligence, the piece that connects technical analysis with the experience collected by the community through sources such as ProtonDB and winetricks.

When Eagle recognizes an application it can now tell you how it identified it, how confident it is about the match, what verdict comes out of community reports and which configurations were used most often; environment variables, overrides or launch arguments appear only when enough evidence exists. This obviously does not mean that a suggestion guarantees compatibility, Wine remains Wine and every system may react differently, but at least you are no longer starting completely in the dark.

![Eagle Intelligence results](/uploads/bottles-65/eagle-results.png)

I care a lot about where this data comes from, so every suggestion shows its source, match type and license, with credits available both on the Eagle page and in the Bottles license section; using data produced by other projects does not make it mine and I want its origin to remain clear, even when that data is distributed inside the Flatpak to make the feature available without an extra download or any configuration.

![Sources, credits and licenses in Eagle Intelligence](/uploads/bottles-65/eagle-intelligence.png)

At the end of the analysis Eagle also proposes a few optimizations that you can choose to apply before launch; every switch remains under your control and the analysis stays available beside those choices, so you can see what changed and why without inheriting a mysterious configuration that becomes impossible to understand tomorrow.

![Optimizations suggested by Eagle](/uploads/bottles-65/eagle-optimizations.png)

## Soda 11, much more than an update

Soda was born because I wanted a runner I could work on directly, built around the way Bottles prepares and launches programs, and that possibility became especially important with the move to Wine 11 because I did not want to change a version number and hope everything would keep working; `soda-11.0-4` collects the work from the previous builds and is the version distributed with Bottles 65.

The new Soda uses Valve's Wine 11 branch, updates Wine Mono to 10.4.1 and restores GStreamer support for both 64-bit and 32-bit programs, which in plain terms means avoiding blank pages, videos that never start and launchers unable to show their media. Real `win32` prefixes are back as well, still needed by some older programs and games that do not behave correctly inside a 64-bit environment, a feature the newer WoW64 builds made much less obvious than it sounds.

![Bottle components with Soda 11 and D7VK](/uploads/bottles-65/components.png)

Testing also exposed a problem in the native Wayland driver: some games started and even played audio, but their window never appeared or the process was terminated, while the same titles worked under Gamescope and initially made the failure rather confusing; the cause was in the conversation between Wine and the Wayland compositor, the part of the desktop that receives windows and decides how they appear on screen, because Wine sent the same presentation request twice and stricter compositors such as Mutter rejected it and closed the connection. Soda now avoids that duplicate request, which lets the Wayland driver and the path required by HDR work there too, without asking the user to learn what `wp_commit_timer_v1` is or accidentally discover that a game appears under Gamescope but not under GNOME.

![Native Wayland and HDR in the bottle](/uploads/bottles-65/wayland-hdr.png)

I also added support for local mod loaders that use `version.dll`, `winmm.dll` or `dsound.dll`, in this case Soda recognizes the library next to the executable and can prefer it automatically without changing the whole prefix.

Anyone who wants to experiment with Transparent Huge Pages can use `SODA_USE_THP=1`; it deliberately remains a variable you must enable yourself because its result changes between games and systems, and forcing it on everyone would make no sense just because it can help in some cases.

## More control over each bottle

Bottles 65 integrates D7VK 2.0 as a managed component, so games based on older Direct3D versions can use Vulkan without installing wrappers by hand and D7VK behaves like any other bottle component; it can be installed, updated or removed while the original files needed to restore the previous state remain safe. It may sound like a feature only meant for very old games, but those are exactly the titles that often send you through guides written years ago where you copy DLLs from random sources, then a few months later cannot remember what changed.

![D7VK in the component manager](/uploads/bottles-65/dll-components.png)

There is also a general FPS limit that works with DXVK and VKD3D, so it does not require Gamescope and can be configured directly in the bottle preferences; the existing limit in Gamescope settings remains available for those who use it, but the frame rate can now be controlled even when that compositor is not installed or simply is not needed.

![The bottle frame rate limit](/uploads/bottles-65/frame-rate-limit.png)

HOTAS devices, joysticks and other controllers that need HIDRAW access can now be selected in the GUI and Bottles passes the correct identifiers to Soda, while the sandbox lets you decide whether a bottle can access input and USB devices; it is important to clarify that HIDRAW selection tells the runner which devices to use but the underlying Flatpak permission remains broader, so this is not per-device hardware isolation. These features are verified with Soda, therefore Bottles shows a warning when you enable them with another runner since that runner may ignore the configuration or read it differently, and I would rather tell you beforehand than leave a switch looking active while nothing happens below it.

![Dedicated sandbox permissions](/uploads/bottles-65/sandbox.png)

Frame generation through `lsfg-vk` keeps its own dedicated page, where you can provide the Lossless Scaling DLL and adjust how frame generation behaves; Bottles stores a private copy of that DLL inside the bottle and excludes it from backups and duplicates because it is a commercial file I cannot distribute and it must be provided by the user, while Bottles handles the integration without asking for external scripts.

![Frame generation settings](/uploads/bottles-65/frame-generation.png)

## Automatic backups, finally

Bottles could already export an entire bottle, which is useful when you want to move everything or create a complete archive, but using that system to protect a game's saves means copying a huge prefix every time when the important data is usually one folder or a handful of files; in Bottles 65 automatic backups are configured for each program through its launch options, where you choose what to copy, where to keep it and how many generations should remain.

The backup is created when the program closes so it contains the latest session data, older copies are removed only after the new one completes and the destination must live outside the bottle, because a backup that disappears together with the prefix it is supposed to protect would be fairly useless (and yes, I checked that too). Restore is manual for now, the dialog opens the backup folder directly and explains where the files need to go, a simpler and more predictable choice for this first version of the feature.

![Automatic program backups](/uploads/bottles-65/automatic-backups.png)

## So, what about Bottles Next?

Bottles Next remains the future of the project and this release does not change that direction, actually this is a good time to explain where it stands because from the outside it may still look like a collection of repositories rather than an application; the backend is complete, WineBridge already talks to it and the CLI and gRPC server let us use it without a graphical interface, so what separates us from Bottles Next now is the application people can actually sit down and use.

That is where our work has moved with [next-ui](https://github.com/bottlesdevs/next-ui), the graphical toolkit we are building in Rust on top of Iced and using as the visual foundation of Bottles Next; the gallery below is not the new application yet, but it is where we put its pieces together, test how they behave and see the interface take shape while the client is being built.

![The next-ui component gallery](/uploads/bottles-65/next-ui-gallery.png)

While we continue that work on Next, I will keep maintaining the current Bottles, fixing the problems that still belong to this code, merging valid contributions and sending Wine, runner, component or dependency reports to the project that can actually solve them.

About the tracker, if you need to open a new issue please use a title that explains the problem and fill in the template with your version, logs and reproduction steps; this release exists because I could move from one clear report to the next instead of spending half of the time asking what was actually broken.

Ok, I think this one can finally leave my computer.

Bottles 65 is out, have fun, break it and this time please give me the logs :P
